# اختبار الحمل (3.5)

**تحذير:** شغّله على مشروع Supabase تجريبي منفصل فقط. السكربت يكتب بيانات (حصص ونقاط) ويسجّل دخولاً بآلاف الحسابات.

## الخطوات
1. أنشئ مشروعاً تجريبياً، شغّل `01` ثم `02` ثم `03`، ثم `seed_test_users.sql` (قد يستغرق دقائق لـ 50,000 طالب؛ جرّب أولاً بـ `n_students := 2000`).
2. في المشروع التجريبي: ارفع حدود Auth Rate Limits (Authentication > Rate Limits) وإلا سترى 429 على الدخول — وهذا حد إعداد لا حد أداء.
3. ثبّت k6 ثم: `k6 run -e URL=... -e ANON=... -e PROFILE=smoke -e N_STUDENTS=2000 k6_load.js`
4. ارفع تدريجياً: `smoke` ← `p2` (10,000) ← `p3` (50,000).

## ما يُحاكى
- 96% طلاب: دخول، فتح التطبيق، نقاطي، ترتيبي. 4% معلمون: دخول، فتح، **حفظ حصة 25 طالباً**، نقاط.
- عتبات النجاح: حفظ الحصة p95 < 500ms، فتح التطبيق p95 < 2s، أخطاء < 1%.

## الحد العملي لآلة واحدة
بضعة آلاف VU فقط (حسب الذاكرة/الشبكة). لـ 50,000 استعمل 5–10 آلات بـ `--execution-segment` أو Grafana Cloud k6.
الأرقام تُقاس من جهة العميل؛ راقب بالتوازي في Supabase: Reports > Database (CPU، الاتصالات) و`pg_stat_statements`.

## متى تتوقع أول اختناق
1. حدود Auth وعدد اتصالات Postgres (استعمل pooler، وخطة بحجم Compute أكبر).
2. `points_calc` للوحة الشرف الكبيرة (يُنصح بتخزين مؤقت أو جدول نقاط مُجمَّع إن تجاوز زمنها الثانية).
3. تحميل `docs` عند فتح التطبيق: استعمل `docs_changed_since` والتخزين المحلي بدل التحميل الكامل.

## الاختبار الدوري
شهرياً وقبل كل إصدار كبير: `p2` على الأقل؛ وسجّل النتائج (p95 لكل مقياس) في جدول لمقارنة الاتجاه.
